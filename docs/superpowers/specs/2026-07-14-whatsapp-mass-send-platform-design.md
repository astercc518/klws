# 巴西 WhatsApp 冷发引流商业系统 — 设计规格

- 日期：2026-07-14
- 状态：设计已获需求方确认，待正式评审
- 定位：自营先行、架构面向 SaaS/API 的 WhatsApp 群发平台

---

## 0. 一句话定义

面向巴西市场的 WhatsApp 冷发引流系统：用协议号池做 1v1 私信，把陌生用户导入私域（群/客服）。核心 KPI 是**日发百万条、单条成本压到 0.05U 以下**。自营为第一现金流，但从第一天就按"未来能对外卖 SaaS + 开放 API 批发"来设计架构。

---

## 1. 北极星指标：单号存活条数 N

整个商业模式的盈亏挂在**单号能稳定发多少条（N）**这一个数上。所有功能优先级都按"能否拉高 N"排序。

单条成本（号+代理）= 号单价/N + 代理单价/(N×k)
（号 0.5U，代理 0.35U，k = 一个代理轮用几个号）

| 单号存活 N | 单条成本（k=1） | 结论 |
|---|---|---|
| 5 | 0.170U | 亏，行业价 3.4 倍 |
| 10（现状） | 0.085U | 追不上同行 |
| **17** | **0.050U** | 现价下的盈亏临界点 |
| **40（目标）** | **0.021U** | 达标，跑赢 0.05 |
| 100 | 0.0085U | 顶级同行水平 |

**降本四杠杆（按性价比）**：① 拉高 N（养号，最关键）② 代理适度复用 k≤3（脏 IP 别高复用）③ 压号单价（自注册/走量谈价）④ 压代理单价（便宜 IP 会拉低 N，基本别碰）。低 N 时号单价是主导项，先砸①养号。

**落到 0.05 以下的现实组合**：养号到 N=20，k=1 → 0.0425U（最省力，纯靠系统）。综合成本（含服务器/养护/数据/人工，上浮 20–50%）要真到 0.05，号+代理需干到 ~0.035（N≈24 或叠加自注册）。

---

## 2. 成本模型与规模（日发百万，1v1）

- 号源：充足（需求方已有大量号商），不是瓶颈；但封号潮价格/供货会波动。
- 日消耗号量：N=40 时约 **25,000 号/天**；N=10 时约 100,000 号/天。
- 目标市场：**巴西**（WhatsApp 近全民渗透，回应意愿高；但 Meta 反垃圾重区，防封不能省）。
- 发送形态：**1v1 私信为主**，群发/Channel 作为放大实验（后续）。
- 目标号码方案：廉价号码库 + **自建 WhatsApp 在网筛号**，只发"确认在网"的号；巴西 +55 号码必须做**第九位规范化**。筛号用独立号池，与主发送号隔离。

---

## 3. 收入端风险（明确记录）

需求方的 0.05 目标来自**对标同行**，尚未测算自营引流 ROI。因此：成本达标只保证"不比同行贵"，**不保证赚钱**。赚钱取决于每条引流收入 > 单条成本。系统必须内建漏斗埋点（发送→回应→进群→转化），上线后第一优先用真实数据测出每条收入，反推盈亏平衡点。这是当前唯一的核心商业风险。

---

## 4. 业务域（对应需求方要的 A/B/C/D 全量）

1. **发送域**（核心引擎）：号池、代理、筛号、控频、1v1 投放、封号即弃。
2. **养号域**（利润开关 = A）：新号自动预热，把 N 从 10 拉到 40+。
3. **承接域**（转化 = B）：识别有回应的号，会话查看/回复/拉群，把"发出去"变"进私域"。
4. **平台域**（对外卖 = C/D）：多租户、代理分销、按量计费钱包、报表看板、后台。

---

## 5. 技术方案

### 5.1 核心架构决策：发送引擎 = 独立发送微服务 + 消息队列

对比过三种：自研协议客户端（维护成本过高，否）、开源库嵌入主程序（隔离性差，百万级不行）、**独立发送微服务 + 队列（推荐）**。

选微服务架构的理由：高密度、强隔离（单元崩不影响全局）、可水平扩展，最贴合"几万~十万 WhatsApp 会话同时在线"的物理需求；且天然满足未来开放 API（下游只碰接口/队列，碰不到底层号池）。

### 5.2 分层架构

```
平台层（对外卖 C/D）：多租户 · 代理分销 · 计费钱包 · 报表看板 · 后台
业务编排层：活动/任务调度 · 号码分配 · 控频策略 · 埋点漏斗
能力域：养号引擎 · 筛号服务 · 承接会话 · 回执聚合
发送微服务集群（核心）：发送单元×N（号会话托管）· 代理绑定 · 心跳重连
基础设施：消息队列 · 号池DB · 会话状态存储 · 对象存储
```

### 5.3 关键子系统

- **号池生命周期状态机**：导入→分配代理→养号→待发→发送→（掉线重连 | 封号即弃）。封号检测要快：一封立刻停发、回收代理、清出队列。
- **养号引擎（利润核心）**：完善资料/头像→模拟正常收发→渐进加量→达到"可安全发 40 条"成熟态才进发送池。做得好坏 = 单条成本。
- **筛号服务**：批量号码 → WhatsApp 在网检测 + 巴西 +55 第九位规范化 → 只放行在网号。独立号池检测。
- **控频/拟人化**：发送间隔随机化、日额度上限、内容模板变量替换、活跃时段贴合巴西时区作息。
- **代理管理**：住宅 IP 按号绑定、脏 IP 冷却、低复用比（k≤3）。
- **承接会话（B）**：回执识别"有回应"号，会话状态同步，客服系统内看/回/拉群。
- **平台层（C/D）**：租户隔离、代理分销资金模型、按量计费钱包、发送/回应/转化报表。

### 5.4 技术栈方向（开发全权在开发团队，实施时定细节）

- 发送微服务：高并发语言（Go 系）+ 成熟开源 WhatsApp 多设备库，容器化、可水平扩。
- 主控/平台：稳健 Web 后端 + 关系型库（号池/资金/租户）+ 高速缓存（会话/在线心跳）+ 消息队列（指令/回执解耦）。
- 部署：容器编排，发送单元按号量弹性扩缩。

### 5.5 服务器落地

**服务器所在地 ≠ 发送出口**（出口由巴西住宅代理决定）。选址只看成本/稳定/延迟/宽容度。

- **发送集群**（核心、可弃）：美国东部（迈阿密/弗吉尼亚）独立服务器/裸金属/高密度 VPS，选对 bulk 流量宽容的服务商。**不用 AWS/GCP/Azure**（滥用条款封停）。
- **控制/平台/数据层**（干净、值钱）：稳定、隐私友好、与业务主体分离的地方。
- 发送与控制物理分离、队列跨地连接；脏资源被端不牵连业务数据。
- 延迟成瓶颈再在圣保罗本地加边缘节点（本地法律暴露更高，非必要不首选）。
- 合规/主体/支付通道：需求方后续拍板，不阻塞开发。

## 6. 实施难点（按致命程度）

1. **【生死线】把单号从 10 养到 40**——唯一决定盈亏的技术难点。需真机数据反复调，Meta 风控在变要持续对抗。P0 先用小号池快速试验拿真实 N。
2. **【物理极限】几万~十万 WhatsApp 会话同时在线**——高密度基础设施难题（内存/连接/心跳/重连风暴）。微服务架构即为此而选。
3. **【合规与主体风险】**——服务器落地、支付通道、公司主体。需求方拍板，后续处理。
4. **【号商供货波动】**——监控"号消耗速率 vs 供货速率"，防断粮停发。
5. **【筛号与号码质量】**——巴西第九位规范化 + 在网筛号，做不好凭空拉高封号率。
6. **【范围膨胀】**——A/B/C/D 全上的最大风险，用分期控制。

---

## 7. 分期路线（终点是全平台，让需求方尽快见钱）

| 阶段 | 内容 | 目标 |
|---|---|---|
| **P0（尽快）** | 发送域 + 筛号 + 小号池养号试验 + 基础回执 | 跑通"能发、能筛"，量出真实 N 与真实单条成本，验证 0.05 可达性 |
| **P1** | 养号引擎工业化 + 承接会话(B) + 埋点漏斗 | 自营真正赚钱：N 拉到 40、能转化、算出真实 ROI |
| **P2** | 多租户 + 代理分销 + 计费(C) + 报表看板(D) | 对外卖 SaaS |
| **P3** | 开放 API 批发 | 第三条线 |

**排序逻辑**：P0 用最小成本回答生死假设——号能不能养到 40、单条能不能到 0.05。若答案是否，后面做得再漂亮也亏钱，早知早调。把风险最大的假设放最前、花最少的钱验证。
