# 高吞吐发送编排层设计（温驻留优先 + 防封闭环）

- 日期：2026-06-30
- 状态：设计草案，待评审
- 适用：wadist（WhatsApp 群发引擎，单机部署）
- 红线：严禁修改 `internal/{billing,dispatch,store,sendgate,cluster}` 的核心业务逻辑与计费/防封事务。新代码放控制面（编排层），仅**调用**这些包的导出方法。

---

## 1. 背景与目标

原始需求（运营提出）：

- 账号池 10W+，动态代理池 10W+，账号国家与代理国家匹配。
- 单账号 5–10 条/天，不可连续发送，每次间隔 ≥1 分钟。
- 内容变量：主题一致、文案随机、变量短链。
- 硬件：AMD EPYC 7542 32C×2、128G、1T NVMe、1 IP。
- 期望节奏：每轮 10000 账号+10000 代理热加载，另 10000+10000 发送，每账号 1 条，1 分钟发完，轮询。

本设计在不破红线的前提下，给出能落地、且把封号率压到最低的架构。

---

## 2. 需求拆解与可行性判定

| 子目标 | 判定 | 关键约束 |
|---|---|---|
| 10000 条/分钟 = 167 条/秒 吞吐 | ✅ 轻松 | CPU <10%，纯 I/O 并发 |
| 连续流水线（边热加载边发） | ✅ 思路对 | 现有 dispatch 已是流水线 |
| 字面"1 万加载 + 1 万发送同时在线"≈ 2 万并发长连接 + 2 万 advisory 锁 | ❌ 单机 Postgres 扛不住 | 每锁钉一条 PG 后端，2 万 ≈ 100G+ 内存 |
| 改为"连续流水线 + ~1500 温会话"达到目标 | ✅ 可行，不破红线 | 代理建连中位数 ≤ ~6s |
| 5–10 条/天、≥1min、国家匹配 | ✅ 现成能力 | sendgate + BindProxy + spintax |
| 真正天花板 | ⚠️ **封号率** | churn 主动制造封号特征 |

**核心结论：吞吐不是瓶颈；封号率是。而原始"秒级连-发-断 churn + 每分钟整轮 + 动态代理每发轮换"会主动生成 WhatsApp 风控特征。**

### 2.1 账号经济学反推真实速率

绑定约束是单账号 5–10 条/天的日上限，不是"每分钟能发多少"：

```
日总量 = 100K × 7.5 ≈ 750,000 条/天
按账号本地白天 16h 自然打散：750,000 / (16×3600) ≈ 13 条/秒
压到 8h：≈ 26 条/秒
```

**稳态只需 ~13–26 条/秒；167 条/秒超配 6–13 倍。** 167/秒只有在账号池涨到 ~130 万、或把全天量压进 ~75 分钟集中爆发（最招封）时才成立。

### 2.2 封号率是成本函数

每账号 = 手机号 + OTP + warmup 沉没成本。日封号率 b：`日烧号 = b × 在线账号数`。churn 容易把 b 从 0.5%/天推到 5%/天，即烧号成本放大 10×。**单位送达成本由 b 主导，不是吞吐。** "安全吞吐"= 让 b 低于经济盈亏线的吞吐，而非硬件上限。

---

## 3. 核心洞察：温驻留 = 稳态需求（Little's Law）

并发约束公式：`R(常驻会话) = τ(发送速率) × T_hold(平均驻留时长)`

```
R=1500 预算下：
  T_hold=60s（会话停留一整分钟，像真人） → τ = 25/s = 1500/min  ✅
  T_hold=10s（短驻留）                    → τ = 150/s（逼近 PG 上限，开始 churn）
  T_hold=5s（churn）                       → τ = 300/s（撑爆 PG，招封）
```

**用 1500 工作集 + 让会话温驻留 ~60s（人类姿态），自然得到 τ≈25/s = 1500/分钟——恰好等于第 2.1 节的账号经济学需求。正确的防封姿态（温驻留）与正确的吞吐（稳态需求）在数学上是同一个点，根本不需要 churn。**

"10K/分钟"作为**峰值能力**保留（临时补发可短时拉 τ→167/s，T_hold 被迫降到 ~9s），绝不作为稳态节奏。

## 4. 架构：控制面 / 数据面分离

```
┌─────────────────────── 控制面（新增编排层，红线安全） ───────────────────────┐
│ ① Eligibility Scheduler   Redis ZSet due:{cc}，score=next_eligible_ms        │
│ ② Working-Set Manager     维持 R≈1500 常驻会话（admit/evict 决策）           │
│ ③ Send Pump               令牌桶 τ/s，选 resident 账号喂数据面               │
│ ④ Risk Governor           消费 health/ban/receipt 信号，调 τ / 驱逐 / 降速   │
│ ⑤ Proxy Affinity          代理终身粘性，仅死亡才 re-bind                     │
│ ⑥ Content/Shortlink       spintax + 唯一短链                                 │
└──────────────────────────────────┬──────────────────────────────────────────┘
                                    ▼ 复用，不改
┌─────────────────────── 数据面（现有引擎） ──────────────────────────────────┐
│ dispatch（select→Hold→render→send→Settle）→ RoutingSender → whatsmeow       │
│ sendgate.Admit（日配额+minGap 原子闸） │ billing │ store │ receipt │ riskbreaker │
└─────────────────────────────────────────────────────────────────────────────┘
```

控制面六组件全是新增，只**调用**数据面导出方法（`Orchestrator.StartAccountWithLock`、`Supervisor.StartAccounts`、`BindProxy`、`sendgate.Admit`、dispatch）。

## 5. 并发控制：四级限流器

| 级 | 限流器 | 含义 | 取值 | 代码旋钮 | 性质 |
|---|---|---|---|---|---|
| W | 预热并发 | 同时建连会话数 | 64–128 | `MaxConcurrentStarts` / `Supervisor.SetLimit` | I/O 绑定 |
| **R** | **常驻工作集** | **同时在线会话数（硬顶）** | **~1500** | **`MaxLockConns` 300→1500** | **PG 后端，真天花板** |
| S | 发送并发 | asynq worker | 256–512 | `AsynqConcurrency` 32→ | 快，会话已在线 |
| τ | 全局发送速率 | 令牌桶 | 稳态 13–26/s，峰值 ≤167/s | 新增，Risk Governor 调 | 防封主旋钮 |

W/R/S 全是 env/config，不碰红线逻辑。

**背压链**（每级满则上游 requeue，绝不丢已计费 charge）：

```
due ZSet ─满?─▶ 工作集有空位?─无→等 ─▶ warm ─▶ Send Pump 令牌─无→等
         ─▶ sendgate.Admit ─拒(pacing/quota)→ Ticket.Release + 重新入 due ZSet
```

> 注意：`sendgate.Admit`（Redis Lua，`q:{jid}:{日}` 日配额 + `p:{jid}` minGap 3s）是**最终原子闸**。控制面只做粗调度，绝不重复计数，精确闸交给它。

## 6. 风控规则引擎

### 6.1 账号生命周期 FSM（叠在 ban_status 之上）

```
        warm 成功            被 Pump 选中发送
 cold ──────────▶ warming ──────────▶ resident ──┐
   ▲                  │ 失败              │发完    │ next_eligible 远(>H)
   │                  ▼                   ▼        ▼
   │              (换代理重试)        cooling ◀── 优雅 logout(留代理)
   │   health<40 / 连续失败 / wa_warning  │
   └──────────────── quarantined ◀────────┘
                          │ 恢复(Heal +5) → cold     │ 永久 → banned/retired
```

### 6.2 四层熔断（阈值=起点假设，由第 11 节 A/B 标定）

| 层 | 规则 | 触发 | 动作 |
|---|---|---|---|
| L1 账号 | 连续失败≥3 / health<40 / wa_warning | 单号 | quarantine 6h（现有）+ 驱逐 + 代理嫌疑标记 |
| L2 代理 | 连续失败≥5（现有 `proxyFailureThreshold`） | 单代理 | 代理下线；关联账号谨慎迁移 |
| L3 国家/ASN 段 | 某 cc 或某代理 /24 段滚动封号率 > 基线×3 | 一段 | 该段 τ 降速 / 暂停激活 |
| L4 舰队 | 全局滚动封号率 > SLO（如 0.5%/天） | 全局 | τ 全局收敛 + 暂停新激活（riskbreaker 兜底） |

复用现有 L0：sendgate 日配额+3s minGap、`effective_quota` warmup 曲线、health（delivered+1/undelivered-2/wa_warning-30）、riskbreaker campaign 自动暂停。控制面只读信号、调 τ、改 due，不改这些逻辑。

### 6.3 反指纹硬规则（控制面强制）

1. 代理终身粘性（见第 7 节）。
2. 去同步：next_eligible 带 per-account 随机相位 → Poisson 到达，杀掉"整点每分钟一波"。
3. 连接后 dwell：warm 成功 → presence(available) → composing(typing) → 人类抖动 200–1500ms → 才让 Pump 选中。**【需扩展 cluster 接口，见第 10 节待决策】**
4. 优雅断开：presence(unavailable) → 停留排空回执 → logout。**【同上，需扩展 cluster】**
5. 本地时区：按账号 cc 本地 09:00–22:00 才 due，夜间不发。
6. 舰队灰度：激活曲线按天 ramp，别一次拉满 10 万。

## 7. 账号轮换与代理亲和

### 7.1 工作集 admit / evict（Residency-aware，非 round-robin churn）

```text
KEEP_WARM_HORIZON H = 90s
每 ~500ms:
  for slot in free_slots(R):
      jid = ZPOPMIN(due:{cc})
      if score(jid) > now: break          # 还没到期
      warm(jid)                            # StartAccountWithLock + dwell
  for jid in resident:
      if has_ban_signal(jid):     evict_quarantine(jid)      # 立即
      elif next_due(jid)-now > H: evict_graceful(jid)        # 远端到期→让位
      # 否则保持常驻（90s 内还要发，摊薄+像人）
```

### 7.2 去同步调度（发后重排）

```text
quota_today   = U(5,10)
active_window = local(09:00..22:00) 按 cc 时区
base          = active_window_seconds / quota_today
jitter        = base × U(-0.4,+0.4)
next_eligible = now + max(base + jitter, 60s)     # 硬保证 ≥1min
ZADD due:{cc} next_eligible jid
```

每账号独立相位→全局近 Poisson；`≥60s` 硬下限满足"间隔≥1 分钟"。瞬间发送仍过 `sendgate.Admit` 的 3s minGap 兜底。

### 7.3 代理轮换规则（最关键的防封）

| 场景 | 动作 |
|---|---|
| 账号首次 warm | `BindProxy(jid,cc)` 一次，写 `proxy_id`/`proxy_url_cache` |
| 后续每次 warm | **复用 `proxy_url_cache`，绝不再调 `BindProxy`** ← 修掉"每轮换 IP"雷 |
| 代理死亡（L2 / `is_alive=false`） | 才 re-bind，优先同 ASN/同 /24/同 cc，账号转 re-warming 低速观察 |
| 100K 动态代理池 | 角色 = 故障转移 + 容量，**不是每发轮换身份** |

> **现状雷**：`store.BindProxy` 每次调用先 `releaseWithinTx` 再 `ORDER BY usage_count ASC` 重挑，即每轮换 IP。修复方式 = 控制面**控制调用频率**（仅首次/死亡才调），不改 `BindProxy` 内部逻辑。

### 7.4 舰队级轮换（100K ↔ 1500 常驻）

任一时刻仅 ~1500/100K 在线。due ZSet 天然限流：账号发完后 next_eligible 推到数小时后，在那之前不可能重入工作集，自动实现"每号 5–10 条/天打散"。全池扫一遍 ≈ 100K/(1500/min) ≈ 66 分钟/轮，每号每轮约 1 条 → 一天 5–10 轮（由 due 间距控制），而非连续 22 轮。

## 8. 内容变量与短链

- 主题一致：模板级常量（campaign_templates）。
- 文案随机：复用 `internal/spintax` 的 `{a|b|c}` 展开，seed=message_id（可复现）。
- 变量短链：**新增短链服务**——每收件人发唯一 code → 存映射 → 301 跳转 + 点击统计。每条消息 URL 唯一，降内容指纹。
- 图谱风险：spintax+短链降内容指纹，但**图谱靠收件人质量**（opt-in 名单、block/report 率回灌 Risk Governor）。

## 11. 灰度压测与安全吞吐标定（canary A/B）

WhatsApp 阈值保密且自适应，唯一靠谱方式 = 用真实封号率反推：

1. 复用 `canary.InCohort(jid, pct)` 分桶：
   - A：churn（hold 5s，每轮 re-bind）= 对照组
   - B：温驻留 60s + 粘性代理 + dwell
   - C：全程常驻
2. 跑 24–72h，按 cohort 统计 `ban_status` 迁移率（DBCollector 加 cohort label，注意基数约束）。
3. 设 ban-rate SLO（按账号成本，如 <0.5%/天），由实测曲线反推每级最大安全激活数/吞吐。
4. Risk Governor / riskbreaker 阈值用该曲线标定。
5. 分级压测 1K/分→3K→6K→10K，每级卡封号率而非算力，拐点 = 这台机器真·安全吞吐。

## 13. 不做（YAGNI）

- 不为 167/s 持续 churn 建设（稳态不需要，且招封）。
- 不做每发代理轮换（招封）。
- 不做整点同步波（招封）。
- 媒体发送仍走现有 text-first（M-send 之外不扩）。

## 14. 验收标准

- 稳态 τ 维持 ~25/s，工作集 R≤1500，PG 连接≤1500，内存≤32G。
- 单账号严格 5–10 条/天、相邻发送 ≥60s（sendgate + 调度双保险）。
- account↔proxy 1:1 终身绑定，无每轮换 IP。
- 全局封号率 ≤ SLO；超标 Risk Governor 自动降 τ / 暂停激活。
- 全程未修改 `internal/{billing,dispatch,store,sendgate}` 业务逻辑；`cluster` 仅在第 12.1 决策允许时新增方法。
