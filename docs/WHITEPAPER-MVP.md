## 1. 产品定位与业务全闭环

一套**多租户**(一个平台服务很多客户)、**按条计费**(发一条成功的短信扣一条的钱)的企业级 WhatsApp 群发 SaaS。三种角色协作完成一笔生意:

| 角色 | 是谁 | 在系统里干什么 |
|---|---|---|
| **销售** | 你的业务员 | 接客户需求,给客户**敲定发送国家 + 每条单价** |
| **管理员** | 你的运营 | 配好发送用的 WhatsApp 账号和代理(产能),**新建客户账号**,客户线下打款后**给客户钱包充值** |
| **客户** | 付费用户 | 登录后**上传号码包、写文案、提交群发**,看自己的进度和账单 |

**全闭环(一笔生意从头到尾):**

```
销售定价(国家+单价)
   ↓
管理员:配账号/代理产能 → 新建客户账号 → 客户线下打款 → 管理员充值入账
   ↓
客户登录 → 上传号码包 + 写 Spintax 文案 → 系统按"条数 × 单价"预估并冻结预算 → 提交发送
   ↓
发信引擎:限速发送(防封号)→ 成功一条扣一条 / 失败的自动退回钱包
   ↓
客户在大盘看进度、在账单中心看每一笔扣费与退款明细
```

## 2. 板块一:前端 UI 与交互验收清单

> 本章是你(老板)的主战场。每个页面都写明:**你能点什么按钮、看到什么数据、钱怎么动、闭环是否成立、验收标准。**

### 2.0 通用:登录与角色(地基)

- 一个登录页,三种角色用各自账号登录后看到**不同的页面**:管理员看全局,销售看自己名下客户,客户只看自己。
- **客户绝对看不到别的客户的任何数据**(号码、文案、账单)。
- 【✅ 验收点】用客户 A 登录,无论怎么点、怎么改网址,都看不到客户 B 的任何数据;退出登录后旧链接立即失效。

> 说明:登录、会话、角色权限、客户间数据隔离(数据库级强隔离)已作为"平台地基"完成,并通过"客户 A 看不到客户 B 数据"的隔离测试。

### 2.1 租户大盘(仪表盘)

客户登录后的首页。**一眼看清"我还有多少钱、最近发得怎么样"。**

**你会看到的数据(只读卡片):**
- 钱包余额(实时,按你的币种/最小货币单位显示)
- 今日 / 本月发送量:成功、失败、发送中(队列里待发)
- 进行中的群发任务列表:每个任务的名称、目标国家、总条数、已发/成功/失败、实时进度条
- 最近账单摘要:最近 N 笔扣费与退款

**你会点的按钮:**
- 「新建群发任务」→ 跳到 2.2 配置页
- 「去充值」→ 跳到 2.3 充值中心
- 点任一任务 →「查看详情」(逐条状态:成功/失败/失败原因)

**钱怎么动:** 大盘只**展示**余额,不在这里扣钱。余额数字必须与账单中心完全对得上。

【✅ 验收点】
1. 余额、今日发送量等数字真实、随发送实时变化(刷新即更新)。
2. 进行中的任务有进度条,会动。
3. 大盘显示的余额 = 账单中心算出来的余额(分毫不差)。

### 2.2 群发任务配置(核心页:号码包 + Spintax 文案)

客户创建一次群发的地方。这是产品的心脏。

**第一步:基本信息**
- 任务名称
- 目标国家(决定单价;单价由销售预先设定,客户在此**只读看到"本次单价"**)

**第二步:上传号码包**
- 支持**上传文件(CSV/TXT)** 或 **直接粘贴**号码列表
- 系统自动:① 校验格式、② 去重、③ 过滤"退订名单/黑名单"(合规:已退订的号码永不再发)
- 上传后显示:**有效号码数 / 重复数 / 被过滤数**

**第三步:编写文案(Spintax 混淆)**
- 文本框输入文案,支持 **Spintax 语法**做"千人千面"混淆,降低被 WhatsApp 判定为垃圾群发的风险。
- Spintax 写法:`{你好|您好|Hi} {老板|朋友}`,系统对每个收件人**随机抽取一种组合**发送,使每条内容都不完全相同。
- 提供「预览」按钮:点一下,随机展示 3~5 条"实际会发出去的样子"。
- (MVP 可选)插入收件人变量,如 `{{name}}`。

**第四步:预估与提交**
- 系统实时计算:**预计费用 = 有效号码数 × 本次单价**。
- 屏幕明确提示:「本次将**冻结** ¥X 作为预算;按成功条数实际扣费,失败部分自动退回。」
- 若**余额 < 预计费用**:「提交」按钮置灰,提示"余额不足,请先充值"(严禁让客户发起一个会把余额发成负数的任务)。
- 余额充足 → 点「提交发送」→ 任务进入发送队列。

**钱怎么动(本页的计费闭环):**
1. 提交瞬间:按"条数 × 单价"**冻结**一笔预算(钱还在钱包里,但被锁定,不能重复花)。
2. 发送中:每成功一条,从冻结额里**真实扣除**一条的钱。
3. 任务结束:**没发出去/失败的条数对应的冻结金额,自动解冻退回**可用余额。

【✅ 验收点】
1. 上传一个含重复号码、含一个已退订号码的号码包 → 系统正确报出"有效/重复/被过滤"数量,且被过滤的号码确实不会收到消息。
2. 输入 `{{你好|您好}}老板` → 点预览,看到不止一种文案;实际发送后,抽查几条收件人收到的内容不完全一样。
3. 提交前预估费用 = 有效号码数 × 单价,数字正确。
4. 余额不足时无法提交(按钮置灰)。
5. 提交后回大盘,余额里"被冻结"的部分正确;任务跑完后,失败条数的钱**确实退回**,最终"扣费 = 成功条数 × 单价"分毫不差。

### 2.3 账单与充值中心

客户看钱、管理员充钱的地方。

**客户视角(看账单):**
- 当前余额、累计充值、累计消费
- **流水明细表**(每一笔都有时间、类型、金额、关联任务):
  - 充值(+)、扣费(−,关联到具体群发任务)、退款(+,关联到失败条数)、冻结/解冻
- 可按时间筛选、导出 CSV(MVP 可选导出)

**管理员视角(充值入账):**
- 选择客户 → 输入充值金额 → 「确认充值」
- MVP 为**线下收款 + 管理员手工入账**(无在线支付网关):客户线下转账,管理员在此录入到账金额。
- 每一笔充值都留痕(谁、给谁、多少、何时),计入审计日志。

**钱怎么动:** 充值 = 余额增加并记一条"充值"流水;扣费/退款由发信引擎自动产生流水。**所有流水必须能加总还原出当前余额**(对账一致)。

【✅ 验收点】
1. 管理员给客户充 ¥100 → 客户大盘和账单中心余额立刻 +100,并出现一条"充值 +100"流水。
2. 发一个任务后,账单里能看到对应的"扣费"明细,失败的能看到"退款"明细。
3. **把所有流水金额加起来,正好等于当前余额**(老板可让开发演示这个对账,这是计费正确性的铁证)。
4. 充值/扣费/退款明细都关联得到具体的人和任务,可追溯。

## 3. 板块二:后端与核心引擎架构要求(给开发团队)

> 本章是对开发团队的强制约束。老板不必细读,但"技术红线"是验收时的拒收依据。

### 3.0 强制技术栈(不接受替换)

| 层 | 强制选型 | 理由 |
|---|---|---|
| 语言 | **Go (1.26+)** | 高并发、单二进制易部署 |
| 数据库 | **PostgreSQL 16 + `jackc/pgx/v5`** | 事务强一致、行级锁、RLS 多租户隔离 |
| 队列/缓存 | **Redis 7 + `hibiken/asynq`** | 异步任务、限速、重试 |
| 部署 | 无头 Worker 节点 + 独立 Web 控制台(`cmd/console`),分进程、分端口 | 扩缩与安全姿态分离 |

### 3.1 高并发事务锁:绝不允许余额透支

- 钱包扣费必须在**单个数据库事务**内完成,且对该客户钱包行加锁(`SELECT ... FOR UPDATE` 或等价行锁),**串行化**同一钱包的并发扣费,杜绝两个任务同时读到旧余额各扣一笔导致透支。
- 采用 **"冻结(Hold)→ 结算(Settle)→ 退款(Refund)"** 三段式:
  - **Hold**:提交任务时,在事务内校验"可用余额 ≥ 预算",通过则把预算从"可用"挪到"冻结";余额不足直接拒绝(幂等:同一任务重复提交不重复冻结)。
  - **Settle**:每条成功,从冻结额扣减并记账。
  - **Refund**:失败/未发条数对应金额从冻结额解冻回可用。
- **每一次资金移动都必须配一条流水(ledger)**,保证"余额 = 所有流水之和"恒等(对账不变式)。
- 充值、退款、扣费都必须落对应流水种类,夜间对账任务定期校验,发现漂移即告警。

### 3.2 Redis 队列与速率限制:防风控(防封号)

- 群发**不允许**瞬间把上万条全塞给 WhatsApp。所有发送经 `asynq` 队列异步化,由发信引擎按节奏取出。
- **多级限速(全部基于 Redis 原子操作,集群一致):**
  - 每账号**每分钟 / 每天**发送上限(令牌桶 / 准入计数,单条 Lua 原子扣减,杜绝并发超发)。
  - **温号曲线(养号)**:新账号每天配额从低到高逐步放开,避免新号大流量触发风控。
  - **健康度熔断**:账号出现异常信号(被限/被封迹象)时自动降速或隔离。
- **Spintax 文案混淆**:同一文案对每个收件人随机变体,避免完全重复内容被识别为垃圾群发。
- 队列必须配置为**消息不丢失**(Redis `noeviction`):已计费的任务绝不能因内存淘汰而丢失。

### 3.3 异步发信与失败退款

- 发信 Worker 从队列取任务 → 调用 WhatsApp 发送 → 按结果走账:
  - **成功** → Settle 扣费,标记该条成功。
  - **失败/超时/无可用账号** → 该条**异步退款**(解冻回可用余额),记录失败原因,绝不扣钱。
- 退款必须**幂等**且与发送结果**最终一致**:同一条消息无论重试多少次,最多扣一次钱;失败则一定退回。
- 任务整体结束时,系统自动结算剩余冻结额(未发部分全额退回)。

### 3.4 🔴 技术红线(踩线即拒收)

1. **🔴 严禁余额透支**:任何并发场景下钱包余额都不得为负。
2. **🔴 严禁计费不一致**:扣钱必有流水,失败必退款,"余额 = 流水之和"必须恒等;严禁出现"钱扣了消息没发也不退"。
3. **🔴 严禁单进程阻塞**:发送、上传、对账等耗时操作必须异步;Web 页面任何操作不得长时间转圈卡死;一个慢任务不得拖垮整个服务。
4. **🔴 严禁绕过限速直发**:所有发送必须过队列与限速,严禁为图快跳过防风控逻辑。
5. **🔴 严禁租户数据串号**:多租户隔离由数据库级 RLS 强制,客户绝不可能读到他人数据;平台账号表对租户角色不可见。
6. **🔴 严禁丢消息**:已接受(已计费冻结)的发送任务不得静默丢失。

### 3.5 数据安全与多租户

- 客户数据按 `tenant_id` 经 PostgreSQL **行级安全(RLS)** 强隔离;客户请求一律走受限角色连接,管理员/销售走系统角色按业务过滤。
- 收件人手机号等 PII 加密存储;退订/黑名单只可追加不可删改(合规)。
- 所有敏感写操作(充值、退款审批、配置变更)写**审计日志**。

## 4. 板块三:开发排期与里程碑(1 个月 · 三阶段 · 4 个周末验收)

> 每个周末你都会拿到一个**在线测试链接**,按下表"老板验收动作"亲自点一遍并打勾。验收不通过则该周不算交付。

### 🟦 阶段一(第 1 周末):环境 + 计费 API 在线可验

**开发交付:** 部署好的测试环境;充值、冻结、扣费、退款、查余额/流水的后端 API + 一个最简管理页(能给客户充值、能看流水)。

**在线测试链接:** `https://test.<你的域名>/admin`(管理员充值 + 流水查看)

**老板验收动作 & 标准:**
- 【✅】给一个测试客户充 ¥100 → 余额变 100,出现充值流水。

- 【✅】**把所有流水加起来 = 当前余额**(对账演示通过)。

### 🟦 阶段二(第 2 周末):队列 + 真实发信引擎在线可验

**开发交付:** `asynq` 队列 + 限速 + 真实 WhatsApp 发信 Worker + 失败自动退款,打通"提交一批号码 → 限速发出 → 成功扣费/失败退款"。

**在线测试链接:** `https://test.<你的域名>/admin/send-demo`(一个内部联调发送页)

**老板验收动作 & 标准:**
- 【✅】提交一小批真实测试号码 → 在你自己的测试手机上**确实收到** WhatsApp 消息。
- 【✅】观察发送有节奏(限速),不是一瞬间全发。
- 【✅】故意混入若干无效号码 → 这些条**自动退款**,账单可见"退款"明细,且未扣钱。
- 【✅】发送完毕后:**扣费金额 = 成功条数 × 单价**,失败部分已退回。

### 🟦 阶段三(第 3 周末):客户端前端 UI 在线可验(主验收周)

**开发交付:** 三个核心页面完整上线——租户大盘、群发任务配置(号码包上传 + Spintax + 预览)、账单与充值中心,串成完整自助闭环。

**在线测试链接:** `https://test.<你的域名>/`(用**客户账号**登录)

**老板验收动作 & 标准(对照第 2 章全部【✅ 验收点】):**
- 【✅】客户登录 → 大盘看到余额与发送统计。
- 【✅】新建任务:上传号码包(含重复+退订)→ 正确去重/过滤;写 Spintax → 预览看到多种变体。
- 【✅】预估费用正确;余额不足无法提交;提交后冻结、发送、扣费/退款全闭环。
- 【✅】账单中心明细齐全、可追溯、余额对得上。
- 【✅】客户 A 看不到客户 B 的任何数据。

### 🟦 第 4 周末:整体压测 + 验收冲刺 + 交付

**开发交付:** 高并发压力测试报告(多客户、多账号、上万条并发)、稳定性与防风控演练、缺陷修复、上线就绪文档。

**老板验收动作 & 标准:**
- 【✅】压测下:余额零透支、计费零不一致、消息零丢失、页面不卡死(对照四条技术红线)。

- ✅ **通过 = MVP 验收完成,可投入试运营。**

## 5. 验收总则(老板的"验收口诀")

> 这 6 条任意一条不过,都可以拒收:

1. **钱对得上**:所有流水之和 = 当前余额,任何时候都成立。
2. **不透支**:余额永远 ≥ 0,并发也不行例外。
3. **失败必退**:消息没发成功,钱一定原路退回。
4. **真能发**:测试手机确实收到 WhatsApp 消息。
5. **不串号**:客户只看得到自己的数据。
6. **不卡死**:页面操作流畅,大批量也不转圈崩溃。

## 6. MVP 范围与风险声明

**MVP 本期做:** 三角色登录、客户大盘、群发配置(号码包+Spintax+预览)、按条计费(充值/冻结/扣费/退款/对账)、限速防风控、真实发信、账单与手工充值、多租户隔离。

**MVP 本期不做(留待后续版本):** 在线支付网关(本期线下收款+手工入账)、销售自助定价后台的完整 UI(本期单价由管理员/销售在后台设置即可)、复杂营销自动化、多媒体富文本模板库、客户自助开户注册。

**风险提示(需老板知悉):**
- **合规与封号风险**:WhatsApp 对群发有平台风控,即便有限速/养号/Spintax,账号仍可能被限或被封;本系统通过限速、健康度熔断、故障自愈接管降低风险,但不能"保证不封号"。群发内容与号码来源的合法合规由业务方负责。
- **真实发信依赖**:第 2 周起需要可用的测试 WhatsApp 账号与代理资源,请提前准备。
- **容量**:具体"能扛多少账号/多少条每分钟"以第 4 周压测报告为准。
